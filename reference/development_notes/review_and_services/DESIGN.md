# DataManager 再設計案

状態: 初期設計・未実装 / 2026-10-30

## 目的

BaseModelを中心に、業務モデル固有のフィールドをRepositoryへ書かずに保存・復元する。
処理の順序と形式固有の制約を明示し、2〜3人で保守できる規模に収める。
この文書は設計の提案であり、公開APIの確定仕様ではない。

## 確認済みの要件

- Python 3.12、Pydantic v2。
- 主な入力はBaseModelとその一覧。明示指定でdict / list[dict]も扱いたい。
- JSONLには異なるモデルを混在させる用途がある。
- 既存のtag付き形式は未運用であり、互換性を必須としない。
- Repositoryはパス、拡張子、読み書き、ロック、アトミック保存を担当する。
- Serializerの専用オプションdataclassと既定値を利用する。
- JSONLの全件保存はメタ行を再生成し、追記は既存メタ行を保持する。
- 設計合意前に大量の実装を進めない。

## 参照したコード

- <project>/mhi/DataManager
- <project>/excel_reports

既存DataManagerにはtext / table / rows / binariesのSerializerがある。
tableはモデル型を直接指定し、rowsはRegistryとtagでモデルを判別する。
この重複を引き継ぐ前提にはしない。

帳票の現行設計資料はexcel_reports/docs/DESIGN.mdとTEMPLATE_SPEC.md。
excel_reportsには新旧ファイルが混在している。ReportGeneratorはReportRecord / ReportItemの
継承を要求するが、report_models.pyは旧定義である。また、旧パターンには現在存在しない
PrintHeaderSpecへの参照がある。結合確認時に整合性を解決する。

## 全体の処理

保存:
値 → モデルの辞書化または明示的なdict入力 → 形式別の文字列・bytes化 → ファイル保存

読み込み:
ファイル読み込み → 形式の解析 → 指定型のモデル検証または明示的なdict出力 → 呼び出し元

責務は次の3つ。ただし、責務ごとに基底クラスやプラグインを作ることは意味しない。

| 担当 | 内容 |
| --- | --- |
| Repository | パス・文字コード・ロック・保存手順・形式選択 |
| Serializer | JSON、YAML、CSV、JSONL、独自形式の解析と生成 |
| モデル変換 | BaseModelと辞書の変換、復元先の選択、モデル検証 |

モデル変換はまず小さな内部関数として検討する。独立した層やFactoryは必要性が出るまで増やさない。
Serializerの外部向け操作はRepositoryから利用し、ファイル操作を二重に実装しない。

## 利用側の候補

単一モデル:

```python
repo.save("user.json", user)
user = repo.load("user.json", User)

repo.save_many("users.jsonl", users)
users = repo.load_many("users.jsonl", User)
```

dictモードは専用の明示的な入口を候補にする。

```python
repo.save_dict("settings.json", data)
data = repo.load_dict("settings.json")

repo.save_dicts("rows.jsonl", rows)
rows = repo.load_dicts("rows.jsonl")
```

boolフラグで返却型が変わる入口より、操作名から検証の有無が分かることを優先する。
一方、公開メソッドが増えるため、最終APIでは利用頻度と比較して決める。

モデル型をRepository生成時に固定する方式も候補として残す。
上記と両方を最初から実装せず、Pylanceでの推論と利用例を比較して一方を選ぶ。

## 混在JSONLとtag

混在ファイルでは、行をどのモデルへ復元するかの情報が必要になる。
利用側のモデルに判別子フィールドを追加することは要求しない。

提案:

1. 利用側は許可するモデル型を指定する。
2. Serializerが行ごとのtagを挿入し、読み込みでは取り除いてモデルを検証する。
3. tagの既定値はモデル名を候補とし、同名衝突はエラーにする。
4. 長期保存・クラス名変更への耐性が必要な場合だけ固定tagを明示できるようにする。
5. ファイルのメタ行に書かれた名前から任意のPythonクラスをimportしない。
6. 未登録のtagはエラー。フィールドの形だけを見て推測しない。

利用側の指定例として、models=(User, Event)のような形を検討する。
その指定だけから任意長のUnionを静的推論できるとは限らない。
list[User | Event]を保証するには、明示的な型付き設定なども含めて小さな試作で確認する。

単一モデルのファイルでは行tagを必須にしない。
単一モデル用と混在用の読み込みは明示的に選び、暗黙の自動切り替えを避ける。
混在形式の予約キーと業務フィールドが衝突した場合はエラーにする。
tagを同じ辞書へ挿入する案と、type/dataの包みを使う案は、実データ例で比較して確定する。

## dictモードの境界

dictモードではPydanticの業務モデル検証を行わない。
ただし、形式としての妥当性、行がdictであること、メタ行の位置などは検証する。
JSON等で表現できないPythonオブジェクトを自動変換することは保証しない。

通常のdict行と、型付き混在JSONLを辞書として読む操作は区別する必要がある。
混在JSONLでtagを除去すると再保存時の復元先情報が失われるため、
タグを含む行を返すか、型情報を別に返すかを公開APIで明示する。
この境界は未確定であり、実装前に利用例と合わせて決める。

## 補助関数の整理

_normalize_aliasesの役割は、外部キーをモデルのフィールド名へ変換すること。
現状はtext / table / rowsに類似実装があり、最上位のキーだけを扱う。
aliasとフィールド名の重複時に、辞書順で値が上書きされる問題もある。

- 先に、Pydanticの入力alias設定だけで満たせる契約を決める。
- serialization_aliasを入力にも受け入れる必要があるか明示する。
- 手動変換が必要な場合だけ、用途を限定した関数を残す。
- ネスト、キー衝突、validation_aliasの扱いを曖昧にしない。
- 「正規化」という名前だけで空文字変換・未知項目除外まで隠さない。
- 公開の読み込み処理から、解析・変換・検証の順序が読めるようにする。

_AttrDict、未定義属性をNoneにする処理、想定上の設定名を複数埋める処理は廃止する。
専用オプションの既定値はSerializerに置き、Repositoryで再現しない。

## 形式別の範囲

| 形式 | 主な検討事項 |
| --- | --- |
| JSON | 単一モデル、辞書、別名、JSON表現可能な値 |
| YAML | テンプレート・既存文書・モデル値の優先順、コメント・キー順保持 |
| CSV | 列構成、空欄、ネスト、可変長配列の表現 |
| JSONL | 単一・混在モデル、メタ行、追記、末尾の整合性 |
| 独自テキスト | 往復可能な値の範囲、階層表現、固定ヘッダー |
| Waveform | 既存の読み取り・peek・復号処理を活用する専用入口 |

CSVで可変長listを暗黙に行展開しない。非対応としてエラーにするか、
セル内JSONなどを明示指定するかを実例から決める。
波形を汎用モデル変換へ無理に統一しない。

## 排他・保存・追記

- ロックは保存先とは別の固定sidecarを使用する。
- ロック不能時はエラー。ロックなしへの自動フォールバックを廃止する。
- 全件保存は同じディレクトリの一時ファイルに書いて置換する。
- YAMLは既存読み込みからマージ・保存まで同じ排他範囲とする。
- JSONL全件保存ではメタ行を再生成する。
- JSONL追記はロック取得後に新規・既存を判定し、メタ整合性を確認する。
- 新規作成と追記のロックを分けない。
- 直接追記は全体置換と同じアトミック性を持たない。
- 異常終了後の不完全な末尾行は検出してエラーにし、自動削除せず明示的な復旧を検討する。
- 通常の追記で全ファイルを読み直さず、先頭メタと末尾の確認で済む構造を検討する。

## Excel帳票との接続

保存・復元は通常のBaseModelを扱う。
帳票生成はReportRecord / ReportItemの契約を要求する。
業務モデルがその契約を満たさない場合は、呼び出し側で帳票入力モデルへ変換する。
Repositoryがitemsやtitleを特別扱いする必要はない。

帳票パターンの選択・抽出・配置・描画はexcel_reports側に置く。
Workbook保存の排他とアトミック保存は共通化の候補だが、
保存と復元を対称に扱うSerializerのI/Fへ帳票生成を押し込まない。

## 実装までの手順

1. この設計の利用例と未確定事項を比較して、公開APIを絞る。
2. 既存Serializerの形式固有処理を、再利用・修正・廃止に分類する。
3. 型推論と混在JSONLの小さな試作で設計を確認する。
4. 合意後にRepositoryと必要なSerializer改修を実装する。
5. JSON / YAML / 独自テキスト / CSV / JSONL / Waveformを実データ例で検証する。

## 必要な検証

- 単一モデルの往復と、混在モデルの型の復元。
- tagがモデルの通常フィールドへ漏れず、予約キー衝突を検出すること。
- dictモードの値と型情報の保持範囲。
- 別名・ネスト・空文字・未知キーの挙動。
- YAMLの既存コメント・キー順・テンプレートの優先順。
- 全件保存でメタ行が消えないこと。
- 同時追記、新規作成の競合、ロック失敗、不完全な末尾行。
- 保存失敗時に既存ファイルを壊さないこと。
- Waveformのload / peek / 復号ハンドラの既存契約。
- Pylanceによる単一モデルと混在モデルの入力・返却型の確認。
