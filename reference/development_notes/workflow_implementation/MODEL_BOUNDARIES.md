# Presetsを中心にしたモデルの境界

## 今回見直す前提

前案では、業務モデルと版ごとの保存モデルを別クラスにする説明を先に置いた。
しかし、目的が違うことだけを理由に、同じフィールド・制約のBaseModelを二重に定義する必要はない。
保存契約は分けて管理する必要があるが、その表現方法を毎回BaseModelの複製に固定しない。

ユーザーから次の実際の流れを確認した。

- Settingsに類するBaseModel、pd.DataFrame、np.ndarrayをファイルから読む。
- それらから必要な値をPresetsへセットし、Presetsで編集する。
- 編集結果をBaseModel等へ置き換え、ファイルへ出力する。

Presetsは編集用のデータ集約として扱う。具体的なクラス定義・項目・変換関数は未確認である。

## 確認した流れに対する推奨案

Presetsを「編集内容の正本」とする。編集可能な同じ値をSettings側にも常設し、
両方の同期を取る構成は避ける。

```text
各ファイル
  ↓ 形式解析・版別変換
Presets（編集する正本）
  ↓ 編集・処理
保存対象ごとの取り出し・版別変換
  ↓
各ファイル
```

Settingsが入出力のための詰め替え容器だけなら、独立モデルをなくす候補になる。
独立した検証・既定値・処理・再利用の役割があるなら、その部分をPresetsの子として使う。
同じフィールドをPresetsへ平坦にコピーし、二つの表現を同時に編集可能にはしない。

旧版用のBaseModelを作る場合も、保存境界の一時的な検証モデルとして使える。
最新Presetsと同じ構造の保存モデルを常設することを前提にしない。
旧形式が単純なら版別の変換関数で足り、複雑なら必要な旧版だけ型で表す。

### DataFrame・配列を含むことの意味

PresetsがBaseModelでも、中身のDataFrame・ndarrayがそのままJSONへ保存できるとは限らない。
現実装の汎用モデル出力はmodel_dump(mode="json")を使うため、
arbitrary_types_allowedだけではそれらの保存規則を定めたことにならない。
現在のCSVも任意配列の展開は行わず、Waveformは読み取り専用である。

設定・表・配列など、保存単位ごとの変換規則をサービスで組み合わせる。
配列の形・dtype・単位、表の列・index・欠損値を、どこまで保持するかを先に決める。
BaseModelへ入れた後のDataFrameや配列の内部変更は、通常の属性代入検証だけでは管理できない。

### 互換情報は編集値と分ける

旧ファイルだけにある値・版・出所は、編集値の別コピーにするのではなく、
対応する保存対象の文脈として保持する。
例えば「Presets + 保存対象ごとの互換情報」を文書単位で扱う案がある。
この外側の文書はPresetの各フィールドを再宣言せず、Presetsへの参照と文脈だけを持つ。

既存loadの戻り値を黙ってこの文書へ変えることはしない。
文書読取API、互換情報の永続化、レコードの対応付けは設計合意の対象。

### servicesの役割

アプリ側servicesは各入力を読みPresetsへまとめ、保存では必要部分を版別に変換して出力する。
現在のObjectFileService等は、その内部で使えるファイル単位の部品であり、
必要がなければ業務servicesからRepositoryを直接呼んでもよい。
ライブラリの汎用RepositoryへPresets固有のフィールドを埋め込まない。

処理結果・進捗・開いたファイル等まで、すべてPresetsへ寄せる必要はない。
編集条件・編集対象データと、実行結果・一時資源の寿命を確認する。
複数の旧ファイルへ分けて保存する場合の一括成功保証は、別途判断する。

## 分ける判断基準

| 観点 | 同じモデルを使いやすい | 分ける意味がある |
| --- | --- | --- |
| 値の意味・単位 | 同じ | 同名でも意味・単位が違う |
| 項目と検証 | 同じ | 必須性や許容値、階層が違う |
| 寿命・独立性 | 一緒に作り、一緒に使う | 別に読み書き・選択・再利用する |
| 変換 | そのまま使える | 集約・計算・既定値の解決が必要 |
| 変更理由 | 常に一緒に変わる | 旧契約を保ったまま内部だけ変える |

形が似ているだけで統合せず、名前や役割のラベルが違うだけで複製もしない。
単なるコピーと、意味を持つ組み合わせを区別する。

## Presetsの役割による3つの候補

### A. Presetsが複数の設定を子としてまとめる場合

```python
class ProcessingOptions(BaseModel):
    threshold: float
    smoothing_window: int = 1

class OutputOptions(BaseModel):
    report_title: str

class Presets(BaseModel):
    name: str
    processing: ProcessingOptions
    output: OutputOptions
```

Presetsは値を二重に宣言していない。ProcessingOptionsの値を使う場所をまとめている。
子モデルが独立して意味を持つなら残す。ただし、同じ役割の巨大なSettingsを別に複製しない。
処理全体はPresetsを受け取り、小さな処理は必要な子モデルだけを受け取れる。

### B. PresetsとSettingsが実質的に同じ値を持つ場合

双方が同じフィールド・制約で、毎回一対一にコピーしているだけなら片方をなくす候補。
実際に使っているPresetsを正本にし、保存にもそのモデルを使う案が自然。
Settingsという名前のクラスを、保存のためだけに残す必要はない。

### C. Presetsが設定を解決・変換した実行入力の場合

ユーザーの指定と、解決後の値は同じではない場合がある。
例: 入力側は「自動で選ぶ」、処理側は解決済みの具体値。
また、複数の設定から計算した値や、その実行でだけ使う資源が入る場合もある。

この場合は、元の指定を保持する設定と、解決済みの実行入力を分ける意味がある。
それでも全フィールドを平坦に複製する必要はない。元の設定を子として持ち、
計算・解決で新たに生じた値だけを実行入力へ追加する形を検討する。

## 保存単位と処理単位は一致させなくてよい

処理の入口がPresetsだからといって、すべてを1ファイルで保存する必要はない。
逆に、1ファイルへ保存するからSettingsという別モデルが必要になるわけでもない。

```text
設定INI       → 処理条件 ──┐
別の設定CSV   → 入力条件 ──┼→ Presets → ユースケース
画面での選択  → 出力条件 ──┘
```

アプリ側servicesは、必要な読取結果を組み合わせる担当になれる。
各Repositoryは自分の保存単位を読み書きし、ライブラリの汎用Serviceは業務項目を知らない。

Presets自体を再利用したい保存データとして扱うなら、全体を保存することもできる。

```python
repository = ObjectRepository(model=Presets, base_directory=Path("data"))
```

この場合も最新の保存構造が同じなら、PresetsFileV5を別に作ることは必須ではない。

## 保存契約をクラスの複製だけで守らない

版ごとに残すべきなのは、保存項目・欠損の意味・既定値・変換規則と、その検証例。
次の順で必要な仕組みを選ぶ。

1. 最新モデルと最新の保存契約が同じなら、同じBaseModelを使う。
2. 旧版との差が少数の改名・補完なら、版別の変換関数とテストで対応する。
3. 旧版に独自の階層・相互制約・型が多ければ、必要な版だけ旧保存モデルを作る。

```text
旧形式の生データ → 版別の変換 → Presets
                                  ↓
                            最新形式で保存
                                  ↓
Presets + 互換保持情報 → v4用の変換 → 旧形式で保存
```

旧仕様が複雑なら、左側にLegacySettingsV4等の検証モデルを置ける。
これを全版に必須にせず、最新Presetsと同じフィールドのモデルを名前だけ変えて作らない。
Repository / Serializer本体へ業務固有の旧キー名は埋め込まない。

BaseModelを共有しても、旧読取の既定値や旧出力の項目は最新版に追従させない。
版別変換の規則と実ファイル例のテストが、過去の保存契約を固定する。

## v6以降への変更

- Presetsが正本なら、その中で必要な型を更新する。業務処理に版分岐を持ち込まない。
- 保存項目を変える場合は版を上げ、旧版を最新Presetsへ変換する規則を追加する。
- 実行中の進捗や計算キャッシュは、通常の保存項目へ混ぜない。
- 現行モデルをそのまま保存する場合は、フィールド追加が保存内容を変えることを変更時に確認する。
- 過去の出力契約は、最新版のmodel_dumpを無条件に流用せず、版別に出力項目を選ぶ。

内部モデルと保存モデルを同じにできることと、過去契約を残さなくてよいことは別。

## 先に確認する課題

1. Settingsや他の子モデルを、Presets以外でも単独で使っているか。
2. Presetsへ設定を入れるとき、そのまま保持するのか、解決・計算・変換するのか。
3. Presetsは値のスナップショットか、変更され得る外部設定への参照か。
4. 複数Presetsで同じ設定インスタンスを共有する場合、変更を他の処理へ波及させないか。
5. 保存したいものは各設定か、処理条件の組み合わせ全体か、その両方か。
6. v4出力で複数の旧ファイルへ分解する場合、途中失敗の扱いをどうするか。

Presetsの統合だけで、旧未使用値の保持問題は解決しない。
互換保持情報は、対応するデータ・レコードへ関連付け、業務モデルとは分けて扱う。

## 現時点の推奨候補

Presetsを編集用の正本に置き、独立した意味のある設定・データモデルだけを部品として残す。
入出力の詰め替えのためだけのSettingsと、同じ構造の最新保存モデルは統合・削除の候補とする。
保存は全体の自動dumpではなく、保存対象・版ごとの変換境界を組み合わせる。
実際のクラス定義と変換処理を確認してから、統合・削除する対象を確定する。

この資料では設計を検討している。アプリ側のモデルや公開APIは変更していない。
