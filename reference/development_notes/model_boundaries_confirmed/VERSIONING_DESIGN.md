# バージョン互換と更新ルールの設計案

2026-10-31 / 設計レビュー用・未実装

## 確認済みの要件

- 内部処理は新しい業務モデルへ揃え、過去のキー名や版分岐を業務処理へ散らさない。
- 旧ファイルにはおおむね版番号がある。版項目が存在しないものはv0として扱う。
- v4以前を読み込み、新形式の通常保存に加え、旧システム用のv4保存を行いたい。
- 旧版にだけある未使用項目は、元の値があれば保持し、なければ指定値または旧版の既定値を使う。
- INI→YAML、CSV→JSONL、TXT→JSONなど、複数のデータ種・形式の組み合わせがある。
- 大きな保存形式・公開APIの変更は、設計合意前には実装しない。

## 何のバージョンを管理するか

| 対象 | 意味 | 更新の例 |
| --- | --- | --- |
| アプリの版 | 実行するソフトウェアのリリース | UIや処理の修正 |
| データの版 | 保存項目・階層・型・意味・欠損時の解釈 | measurement_valueの追加や単位変更 |
| 保存形式の仕様 | JSONLのメタ構造、独自テキストの文法等 | メタ行の仕様変更 |

数値を連動させない。現在のJSONLのschema_version=1や独自テキストの# v1は、
業務データのv4 / v5ではない。業務版の読み取り位置・書き込み位置はデータ種と形式ごとに定義する。
INIの版項目名やセクションを推測してハードコードしない。

管理する数字を過剰に増やさず、まずはデータ種ごとの整数の版と、既存の形式識別を使う案を推奨する。
データ種が違えば、設定v6・測定結果v5が同じアプリで共存してよい。

## データの版を上げる基準（推奨案）

| 変更 | データ版 |
| --- | --- |
| 保存されない一時変数、内部計算の補助項目 | 上げない |
| Python内の名前だけを変更し、保存名・意味は維持 | 上げない |
| UIの表示名、コード整理、JSON字下げ | 上げない |
| 永続化する項目の追加・削除・改名 | 上げる |
| 保存する型、単位、階層、値の意味、必須性の変更 | 上げる |
| 欠損値の意味や欠損時の既定値を変更 | 上げる |
| 形式だけの変更で論理データ仕様は同じ | 形式の設定を変える。データ版を上げる必然性はない |

新しいキーが旧読取側で無視できる追加でも、保存仕様を変えたことを追跡するため版を上げる方針。
「版を上げること」と「旧システムが読めなくなること」は同じではない。
型や階層が変わる形式変更は、データ仕様の変更として扱う。

## v6になったときのBaseModelと、Presetsの位置付け

保存契約を版ごとに残すことと、同じフィールドのBaseModelを版ごとに複製することは分けて考える。
[MODEL_BOUNDARIES.md](MODEL_BOUNDARIES.md)に、Presets / Settingsの役割から構成を選ぶ案をまとめている。

Presetsはユーザーの説明では、BaseModel・DataFrame・ndarray等から集めた値を編集する正本である。
その名前を保って最新の項目へ更新するが、すべてを1ファイルへ自動dumpする前提にはしない。
Settingsが独立した意味のある部品ならPresetsの子として使い、値を平坦にコピーして二重管理しない。
同じ値・制約を一対一にコピーするだけのSettingsや最新保存モデルは、独立クラスにする必然性がない。

最新の保存対象と業務モデルが同じなら、同じBaseModelをそのまま使ってよい。
ただし、Presets全体の編集単位と、設定・表・配列の各保存単位は分けて考える。
旧版との差が改名・補完等に限られる場合は、版別変換関数と検証用のファイル例で契約を固定する。
旧仕様の階層・型・相互制約が複雑な場合だけ、必要なLegacySettingsV4等の検証モデルを置く。
この判断を全版一律のクラス分離や、長い継承チェーンへ一般化しない。

```text
旧形式の生データ → 版別の変換 → 最新のPresets
                                     ↓
                              最新形式へ保存

最新のPresets + 互換保持情報 → v4用変換 → 旧形式へ保存
```

内部の型を共有しても、旧読取の既定値や旧出力の項目は最新モデルへ自動追従させない。
版別変換・出力規則・実ファイル例のテストが、過去の保存契約を固定する。
意図的な仕様変更を同じ版へ紛れ込ませず、不具合修正はその契約に沿って検証する。

読める版と書ける版は別に管理する。v6導入後も全版へ書き戻す義務はない。
まず読取v0〜v6、通常保存v6、互換出力v4を対象にし、v5出力は用途が出た場合に追加する案。

## 版の読み取り

1. 形式を解析し、モデルの未知キー除外などを行う前の値を取り出す。
2. データ種・形式ごとに決めた場所から版を読む。項目がなければv0。
3. 版に対応する旧契約の検証と、最新内部モデルへの変換を行う。
4. 元の旧項目と出所を、内部モデルとは別の互換保持情報として関連付ける。

空文字・不正な値・未対応の未来版を、欠損と同じv0へ落とさない。
整数文字列の許容などは形式ごとの版取得規則で決める。
複数の版項目が食い違う場合も、どちらかを推測で選ばずエラーにする案。
ファイルの版から任意のPythonクラスをimportせず、定義済みの変換だけを使う。

## v4出力の値の優先順

項目の役割を分ける。業務で使う項目と、旧版にだけある保持項目を同じ規則で上書きしない。

| 対象 | 優先する値 |
| --- | --- |
| 最新モデルと対応する旧項目 | 処理後の最新モデルからv4へ変換した値 |
| 旧版だけの項目で、元のキーが存在 | 元の値 |
| 旧版だけの項目で、元のキーが不存在 | 互換出力用の指定値、次にv4の既定値 |
| 元に存在せず、省略が許される項目 | 必要に応じて省略 |
| v4で表現できない値 | 変換方針がなければエラー |

存在判定はキーの有無で行う。False・0・空文字・Noneを「ない」として既定値へ置き換えない。
旧項目はモデルによる未知キー除外より前に取り出す。未使用値を無理に業務型へ変換しない。
v4として読み込んだ元文書の保持対象をベースに、対応する業務項目と出力版だけを更新する案。
新形式の生データ全体をv4へコピーし、新しいキーを旧形式へ漏らすことはしない。

## 実装前に表へ出す課題

### 1. 互換保持情報を保存・再読後にも残すか

メモリ上だけの保持では、v4→v5保存→アプリ終了→v5読取→v4出力で元の未使用値を失う。
この経路も保証するなら、互換保持情報を永続化する必要がある。

| 候補 | 利点 | 注意点 |
| --- | --- | --- |
| v5の保存物内へ互換保持領域を設ける | データと一緒に移動でき、1ファイルの原子的保存が使える | 新形式の予約領域・名前を決める必要がある |
| 別の補助ファイルへ保存 | 新しい業務データの見た目を単純にできる | 2ファイルの整合性と紐付けを別途扱う |
| 元の旧ファイルを参照 | 新形式へ旧項目を持ち込まずに済む | 元ファイルの移動・削除・変更の影響を受ける |

最初の案を推奨候補とするが、保存形式が変わるため未合意のまま実装しない。
互換保持情報は業務BaseModelのフィールドへ混ぜず、保存文書・読取結果のメタ情報として扱う。
既存loadの戻り値を黙って別の型へ変更せず、明示的な文書読取API等を比較して決める。
SerializerやServiceにlast_loadedのような共有状態で保持しない。

### 2. CSV / JSONLの行ごとの紐付け

並べ替え・削除・複製後も、どの旧項目がどのレコードに対応するか分かる必要がある。
ファイル全体のメタ行だけで全行の旧項目を保持する設計にはしない。
レコードと文脈を一体で扱うか、安定したレコードIDで関連付けるかを決める。

### 3. 欠損・空文字・None・明示削除の区別

読み込み時に存在しなかった項目と、ユーザーが意図して空にした項目は別。
自動の空欄変換・既定値投入が、旧値を残すか削除するかの判断を隠さないようにする。
明示削除を元の値で復活させないため、更新として受け取る操作も設計する必要がある。

### 4. v6の値がv4で表現できない場合

新しい列挙値、数値範囲、単位、複数値等は、旧形式へ一意に変換できるとは限らない。
無言の切り捨てをせず、拒否・変換・省略のどれを採るか項目別に定義する。
未使用の旧項目へ使う既定値も、最新モデルの既定値とは分けて固定する。

### 5. 「体裁」の保証範囲

キー・セクション・値の表記を合わせることと、コメント・順序・空白・文字コードまで
元文書と同じにすることは別の保証。INI / CSV / TXTそれぞれで必要な範囲を確認する。
特にConfigParserで構造を読めるだけでは、元コメント等の保持まで保証したことにはしない。

### 6. 古い出力機能の維持範囲

すべての組み合わせの相互変換を汎用グラフとして実装しない。
読み込みの変換と、必要な互換出力先の変換を分け、対応表で明示する。
旧システムでの表示・処理まで含む受け入れ確認が必要。

## 更新時の小さなルール

保存項目を変更するPRでは、次の情報を同時に記録する案。

- 保存仕様が変わるか。変わるならデータ版を上げる。
- どの旧版を読み込めるか、どの版へ保存できるか。
- 追加項目の旧データへの補完値と、欠損時の意味。
- v4へ出せない値の条件と扱い。
- 互換保持情報をどう引き継ぐか。
- 代表的な旧データの読取、最新形式の再読、旧出力の受け入れテスト。

業務コードでは最新モデルだけを使い、版分岐は入出力の境界へ集約する。
内部計算のための変数追加だけで版を増やさない。

## 現在の実装との関係

これは設計案。現在のRepository / Serializer / Serviceにバージョン変換はまだ実装していない。
INI Serializer、版検出、旧値の保持、バージョン別の出力設定、文書読取APIが追加検討の対象になる。
既存のロック・原子的保存・専用オプションを使い、業務固有の変換はアプリ側から渡す構成を目指す。
