# 加工・解析・帳票と外部反映の検討メモ

2026-10-31 / 要件整理。実装追加ではない。

## 確認済み

- 加工後の初回保存では、必要なファイル一式が揃うことが必要。
- 解析処理以降は、解析によって変更されたファイルだけを保存する。
- 一つの解析データはフォルダ内の複数ファイルで構成する。単一ファイルへの結合はしない。緊急対応や検証で一部ファイルを手修正して再読み込みできることが要件。
- 帳票は閲覧・報告用の出力。Excel / CSV / JSONLの帳票を加工・解析へ読み戻さない。
- 用途別Presetsは必要な項目を明示する。各Settingsの子への一律の置き換えはしない。
- 版変換は辞書間の隣接版upcast / downcastを連鎖させる。全版のBaseModelや工程別の版モデルは作らない。
- 通常保存は最新。旧版出力は明示指定し、その版にない項目を除外する。
- 旧項目は保持方針を区別する。以前使っていて現在は使わない値は基本的に維持する。保存されていただけで以前から見ても使ってもいない値は最新版で廃止でき、旧版出力でも元値の引き継ぎは不要。旧読取側の必須項目は、省略可否や固定の既定値が必要かを旧仕様から確認する。
- 元の決定版への上書きは想定しない。v0.3.0で上書き拒否を既定とし、更新時だけoverwrite=Trueを明示するAPIを実装済み。

## 今後の検討材料：DB・進捗情報の集約

ユーザーから、解析実行時のDB書き込み、および解析データフォルダと同じ階層にある別属性の集約フォルダへの最新状況反映があるとの説明を受けた。
これらも将来の接続先として考慮するが、現時点で汎用イベント基盤、分散トランザクション、DB層の実装を追加しない。

- 解析処理、解析データの保存、DB書き込み、集約情報の更新の実行順と成功条件。
- ファイル保存後にDBや集約先の更新だけ失敗したときの表示・再試行。
- 再試行でDBの重複登録や古い進捗への巻き戻りが起きないための対応付け。
- DB / 集約先が解析データから再構築できる補助情報なのか、独立して保持すべき正本なのか。
- 解析実行中の進捗と、結果の保存完了を区別する必要性。
- 複数の解析が同じ集約先を更新する場合の競合。

これらの手順はアプリ側servicesで扱う候補。汎用SerializerへDB更新や進捗反映を埋め込まない。

## 今回確定したことと実装時の注意

- 格納単位はフォルダ内の独立ファイル一式。初回は一式を揃え、解析後は変更分だけ保存する。
- 外部で一部ファイルを書き換えてから再読する運用を許容する。隠れたキャッシュや互換情報で編集前の値へ戻さない。
- 手修正後も構文・版・値を検証する。複数ファイル間の不整合は検出して説明し、自動的に旧値へ巻き戻さない。
- 全旧項目を無条件で保管する設計は採らない。維持対象と廃止対象を、データ種別の互換変換で明示する。
- 維持対象の値は保存・終了・再読後も引き継ぐ。廃止対象の元値を旧版出力のために復元する義務はない。
- 廃止した項目の元値を保持しないことと、旧形式の必須キーまで省略できることは別。実ファイル仕様に合わせて扱う。
- ロックに従わない外部エディタによる同時書き換えは、sidecarロックだけで排他できない。手修正後の明示的な再読を基本とし、必要なら保存前の変更検出を別途検討する。

これらは以前の「全旧項目を互換情報として保存する」案を置き換える。DB / 集約フォルダへの外部反映は引き続き今後の検討事項。
## 2026-11-01：追加合意と具体化方針（v0.3.1で反映）

### 初回保存の失敗

- 初回一式の保存が途中で失敗したら、今回新規作成したデータファイルを削除し、最初からやり直す。
- 元データ・既存ファイル・他処理のファイルを削除対象へ含めない。新規保存先と編集セッションの排他を前提に、今回の作成物だけを追跡する。
- 削除にも失敗した場合は、元の保存失敗と残ったファイルを通知する。ロールバック成功と偽らない。
- この失敗時の後始末は、強制終了・電源断まで含めた複数ファイルの原子的保存を意味しない。
- 解析後の変更ファイルの更新を、この初回新規保存の削除処理へ流用しない。

### DB / 集約先の反映失敗

- 解析データの保存は成功として扱う。外部反映の失敗で解析データを巻き戻さない。
- ユーザーの画面では「外部反映待ち」の常設表示は現実的でないとのこと。
- UI案：「外部情報を更新」ボタン等で保存済みの解析データから再反映する。ボタン名と配置は提案段階であり、画面を変更したわけではない。
- 失敗時の通知とログを残す案。再反映で解析処理をもう一度実行したり、未保存の編集値をDBへ送ったりしない。
- 接続先ごとに再実行の重複防止・最新性の扱いを決める。DBと集約フォルダは同じ取引ではないため、片方だけ失敗した場合を区別する。

### 編集中の排他

- 同じ解析データ一式は、一度に一人・一画面だけが編集する。
- portalocker等でフォルダ単位の編集セッションをロックし、読み込み開始前から編集終了・画面を閉じるまで保持する方針。
- 現在のRepositoryのファイル単位ロックは短時間のI/O保護。編集セッションのロックとは別の役割。
- ロック済みなら二重編集を開始せず、使用中であることを通知する。自動マージ機構は作らない。
- ロックファイルの存在だけを使用中の判定にしない。実際のOSロックを取得し、正常終了時に解放する。
- 一般の外部エディタはこのロックへ従わないため、手修正はアプリの編集セッションを終了してから行い、再び開いて読み直す運用とする案。

追加の汎用基盤は先に増やさず、初回保存の後始末と編集セッションをアプリ側servicesへ具体化する。外部反映ボタンと接続先の処理は実画面・実DBが確認できる段階で扱う。

v0.3.1実装状況：初回保存の後始末と編集期間中のフォルダ排他をアプリ接続例へ実装した。
外部反映は成功・失敗を分けて返し、保存済みデータから全接続先または失敗先だけを再実行できる。
集約JSONの更新例は実装済み。実DB・実画面は未接続。使い方・保証範囲はEDITING_AND_EXTERNAL_UPDATES.mdを参照。

## 2026-11-01：保存検証・外部JSONL・YAMLコメントの追加合意（未実装）

- 保存直前に値をまとめて再検証し、不正なら保存しない。代入時検証を一律に必須化しない。
- 外部のメタなしJSONLは取り込み専用とする。保存先には内部形式のメタ付きJSONLを使う。入力用設定でそのまま出力し、再読不能になる非対称なAPIは整理する。
- 版変換後のYAML出力でも、元文書のコメントを保持する。テンプレートのコメントだけで代替しない。

実装時の注意：

- 保存検証は設定だけでなく測定行にも適用し、全行の検証を終えてから書込を始める。検証に伴う補正値を使う場合は、検証結果と実際の保存値を一致させる。
- 汎用モデルの再検証はvalidation_alias / serialization_aliasが異なる場合も考慮する。独自の暗黙alias補正を再導入せず、Pydanticの公開APIと対応版を確認する。
- YAMLのコメント保持を、旧キー・旧値を丸ごと残すマージと同一視しない。維持対象の値だけを引き継ぎ、廃止した項目を復活させない。
- 改名したキーのコメントは対応先へ移す必要がある。元の値を破棄する方針と両立させ、コメント保存のために旧文書全体の値を永続化しない。
- 保存先を別名にする運用もあるため、既存の保存先からコメントを読むだけでは不足する。読取元からコメントを引き継ぐ文脈の受け渡しを設計する。

この節は方針確定の記録であり、現在のコードへ反映済みであることを意味しない。
