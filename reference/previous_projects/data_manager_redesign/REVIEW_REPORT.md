# 再設計コードのレビューと改善

2026-10-31 / v0.2.1

## 今回の変更

services.pyへObjectFileService / RowsFileService / WaveformFileServiceを追加しました。
固定するのはファイル名・Repository・任意のテンプレートだけです。
例外・型変換・ロック・保存処理は既存の担当へ委譲し、サービスに別の実装を持たせていません。

アプリ側の組み立て例をexamples/application_services.pyへ追加しました。
業務モデルはライブラリへ持ち込まず、ユースケースで使う窓口を一度だけ構成します。

## 再現して修正した問題

| 問題 | 修正前の挙動 | 修正後 |
| --- | --- | --- |
| JSONの重複キー | 最後の値だけが残る | 入れ子を含めSerializationError |
| JSONの1e999等 | Pythonのinfとして受け入れ、再保存できない | 有限値として表現できなければエラー |
| dictの入れ子の整数キー | JSONで文字列へ勝手に変わる | 辞書・配列を辿り、全階層でstrキーを要求 |
| 独自テキスト内のJSON値 | 重複キーや数値の問題が残る | JSON / JSONLと同じ値解析を利用 |
| YAMLの循環エイリアス | round-trip構築時にNoneへ変わる場合がある | 値構築前に構文ノードを検査して拒否 |
| アンカー付きのYAML真偽値 | ScalarBooleanというint派生型で戻る | 通常のboolへ戻す。他の編集用スカラーも通常型に揃える |
| 再帰モデルの空CSV | 列推定が無限に再帰しRecursionError | ConfigurationErrorとし、有限のcolumns指定を要求 |
| ロック待機時間のNaN / inf | 不正値がそのままロックへ渡る | 共通の有限・非負数チェックで構成時に拒否 |
| 外部ヘッダー関数の誤返却 | None等でAttributeError | 戻り値・マッピング・開始位置を確認してWaveformFormatError |
| 型設定への値・空タプル等 | set / issubclass由来のTypeErrorになる場合がある | ConfigurationErrorに揃える |
| 混在型の暗黙の復元 | 内部APIで先頭型を選べてしまう | 混在時は選択済みクラスを必須にする |
| 単一Objectへの混在型指定 | 型注釈を経由しないと構成できてしまう | 構成時に拒否 |
| JSONLの未知metadata設定 | 設定が無視され、メタを本文として読む場合がある | required / absent以外は構成時に拒否 |

不正な入力を以前より厳しく拒否する変更があります。
重複キーの片方を残す動作や、キーの暗黙変換に互換性を持たせていません。
既存の正常な保存形式・通常のモデル入力のAPIは維持しています。

## 小さなリファクタリング

- JSON値の解析規則をJSON / JSONL / 独自テキストで共有。
- ロック待機時間の検証をfile_ioへまとめ、各Repositoryで同じ条件を使用。
- モデル型の検証を、setとissubclassを使う前へ移動。
- コメントは目的・前提をdocstringへ、具体的な判断理由を処理の近くへ配置。
- 非公開属性、名前の省略抑制、docstringの空白、None戻り値注釈の省略を維持。

## 実装せず、提案に残したこと

### CSVの任意配列と、入れ子全体がNoneの表現

可変長配列の行展開と、親がNoneの行・子フィールドがある行が混在するCSVには、
欠損と空欄をどう区別するかの取り決めが必要です。
セル内JSON、専用のnull表記、別表などは保存形式を変えるため、今回は追加していません。
現在の衝突・非対応エラーを維持します。

### メタなし外部JSONLの読み取り専用API

metadata=absentは入力の全行を本文として読む設定ですが、saveは内部形式のメタを生成します。
同じ設定で保存して再読すると整合しません。現在の契約では外部入力用に分けて使います。
読み取り専用サービスか、入力・出力の形式契約を分ける設計が必要です。
既存の読取契約を変えるため、今回は提案に留めています。

### 生成済みBaseModelの業務制約を保存時にも再検証するか

現在は、受け取ったBaseModelは既に検証された値として扱います。
モデルの作成後にvalidate_assignmentなしで変更した値や、model_construct / model_copyで
意図的に検証を省略した値を、保存のたびに全制約で再検証する契約にはしていません。
必要なモデルではvalidate_assignment=True等の入力側の方針を検討してください。
ライブラリ側で再検証を必須にする場合は、入力aliasと出力alias、モデルvalidatorの副作用、
性能の取り決めが必要です。独自のalias正規化を再導入する変更は行っていません。

### 複数ファイルの一括保存、JSONLの障害復旧、Excel保存との結合

サービスは複数ファイル全体の原子性を提供しません。UoWを採用しない既存方針を維持しています。
直接追記の途中障害と、破損末尾をどう修復するかのAPIも未実装です。
Excel帳票は別の生成処理として残し、保存部分の統合は今回の変更範囲に含めていません。
