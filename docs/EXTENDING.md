# モデル・独自形式・版互換を追加する

## 保存版と処理入力を独立させる

処理用のSettings/Presetsは現在の意味を表し、V2Presets・V3Presetsのように版ごとに増やしません。外部辞書を隣接版のupcastで現在版へ変換し、現在のモデルを検証します。旧版保存は現在の保存辞書からdowncastを逆順に適用します。版がないものはV0です。

具体例はDataManager/settings_versions.pyとexamples/workflow.pyです。サンプルはV0→V1→V2→V3とV3→V2を実装しています。V4/V5/V6の実業務仕様が実装済みという意味ではありません。

```mermaid
flowchart LR
    F[旧形式のファイル] --> P[形式固有の読取: dictへ]
    P --> C[V2からV3など隣接版の変換]
    C --> M[現在のSettings + 維持する旧項目]
    M --> U[用途別Presets・処理]
    U --> W[現在版の保存辞書]
    W --> N[現在版の保存]
    W --> B[必要ならdowncast]
    B --> O[旧版の別ファイルへ保存]
```

昔使っていたが現在は使わない値はretained_valuesとして保持します。昔から使わず廃止を決めた項目は変換時に捨て、旧版出力へも持ち戻しません。現在の新項目が旧版に存在しない場合は、downcastで除外します。必要な旧版項目の補完値は、その版のキャスト関数に明記します。

処理結果の値が変わるたびに保存版を上げる必要はありません。項目名・型・単位・意味・必須条件・保存構造が変わり、従来の読取では正しく解釈できなくなる変更を保存版の更新対象とします。同じキーでも意味や単位を変えるなら変換が必要です。処理アルゴリズムの識別は保存スキーマの版と別に考え、今後実業務の追跡要件が決まった時点で扱います。

## 旧text・拡張CSV・独自形式

拡張子だけでは形式の意味が決まらないものは、汎用Serializerへ業務条件を足し続けず、対象固有のSerializer/読取関数をDataManagerに置きます。その役割はバイトや文字列を辞書・行へ戻すことです。項目名の改名や版の補完はキャスト関数、業務モデルの検証は現在モデルが担当します。

同じ拡張子でも仕様が違うものは、用途に合うSerializerをRepositoryへ明示設定します。ファイル本文から自動推測することは前提にしません。configparser→YAML、CSV→JSONLの移行も読取形式と出力形式を別に選べば対応できますが、個別の旧仕様に合う読取実装は追加が必要です。

JSONLの異種モデルはフラットな通常キーの型判別子を使用できます。既定名は`type`です。JsonlSerializerの`tag_field`で変更でき、業務フィールドとの衝突を検出します。`model_tags`でモデルクラス名から独立した固定名を設定できます。モデル型の登録と実行時の検証を行うため、ファイルから復元できます。型注釈が単一モデルならその型、混在ならUnionになります。typing.castだけで安全に復元する構成ではありません。

波形の境界はWaveformOptionsへheader_readerを注入します。公開例は長さ付き合成ヘッダーであり、社内の実フォーマットではありません。
